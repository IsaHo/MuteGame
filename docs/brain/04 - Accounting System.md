# سیستم حسابداری

## هدف

حسابداری MuteGame باید سریع برای اپراتور و قابل حسابرسی برای مالک باشد. الگو از QuickBooks/Xero گرفته می‌شود: نمای ساده جریان پول، مطالبات واضح و دفتر تراکنش قابل پیگیری.

## اصول غیرقابل مذاکره

1. `users.credits` و `users.debt` cache عملیاتی‌اند؛ حقیقت مالی **ledger** است.
2. هیچ `UPDATE credits = credits +/- ?` خارج از سرویس مالی مجاز نیست.
3. هر تغییر پولی یک سند با `id`, `user_id`, `type`, `amount`, `before`, `after`, `reference`, `actor`, `created_at` دارد.
4. بدهی پس‌پرداخت **Accounts Receivable** است؛ ایجاد بدهی درآمد نقدی نیست.
5. پرداخت بدهی cash-in است و مانده دریافتنی را کاهش می‌دهد.
6. هر mutation باید idempotency key داشته باشد تا reconnect دوباره پول کم نکند.

## رویدادهای مالی

- `credit_charge`: دریافت پول و افزایش کیف پول.
- `session_usage`: مصرف کیف پول بابت بازی.
- `debt_accrual`: مصرف پس‌پرداخت و افزایش مطالبات.
- `debt_payment`: دریافت پول و کاهش مطالبات.
- `shop_sale`: فروش شاپ بر اساس روش پرداخت.
- `refund`, `adjustment`, `expense`.

## صفحه ساده حسابداری

### Overview

- موجودی نقدی/دریافتی دوره
- درآمد بازی
- فروش شاپ
- هزینه
- سود خالص
- مطالبات باز

### Receivables

- فهرست بدهکاران
- aging: امروز، ۱ تا ۷ روز، ۸ تا ۳۰ روز، بالای ۳۰ روز
- پرداخت جزئی/کامل
- statement هر کاربر

### Cashbook

- خط زمانی تمام دریافت‌ها و پرداخت‌ها
- فیلتر تاریخ، نوع، کاربر، اپراتور و روش پرداخت
- export CSV

### Shift Close

- موجودی اول شیفت
- پول نقد، کارت، انتقال و کیف پول
- فروش بازی و شاپ
- هزینه و کسری/اضافه صندوق
- تأیید دو مرحله‌ای و قفل گزارش بسته‌شده

## معیارهای صحت

- جمع ledger هر کاربر = مانده عملیاتی.
- جمع پرداخت بدهی در گزارش = تراکنش‌های `debt_payment`.
- سود با جریان نقدی یکی نیست.
- restore backup باید reconciliation بدون اختلاف بدهد.
